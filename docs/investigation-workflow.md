# 分楼层排查与发现烟头后的录像回查

本流程用于缩小人工回查范围。物体检测、来源楼层判断和责任人认定是不同问题；运动候选不等于烟头，画面中的楼层也不等于物体来源。

## 单机分区与双机同步

### 一台电脑、一台摄像机：按楼层区间逐步观察

可以先拍摄 1–10 楼，再拍摄 10–20 楼，然后继续向上排查。相邻区间保留重叠楼层（例如第 10 楼），记录每次拍摄的开始/结束时间、朝向、楼层范围和遮挡情况。根据实际画面清晰度再缩小到更小范围。

这是一种分区收集线索的方法。由于各区间在不同时间被拍摄，**某区间未检出不能直接排除该楼层**：该时段可能没有发生抛物，也可能存在遮挡、画面外路径、模糊或漏检。只能写“该时段未观察到”，不能写“已排除 1–10 楼”。镜头转换后的新角度不能解释转换前未拍到的部分。

### 两台电脑、两台摄像机：同时覆盖不同区间

两套设备可同时覆盖 1–10 楼与 10–20 楼，重叠区应足够让同一个下落物体在两路画面中被关联。每台电脑分别运行本项目，各自录制原始 MKV，保存到各自的项目数据目录。

- 分别配置 `camera.id: camera01` 与 `camera02`，标明各自覆盖区域。
- 开拍前同步系统时间，并拍摄两路都能看到的共同时间参照；记录实测时钟偏差。单纯把系统时钟设成一样不能证明帧级同步。
- 两路分别记录分辨率、帧率、曝光、拍摄区间与中断时间。不要仅凭相同秒数或相似轨迹认定是同一个物体。
- 同一物体从上方进入下方画面，可增加对路径的了解；只有直接拍到物体从具体开口抛出的连续过程，才提供更强的来源线索。
- 风、透视、抛出方向与遮挡都会影响轨迹，不能把轨迹简单向上延长后指定楼层。

**当前没有自动双机标定、时间对齐、轨迹融合或楼层识别功能。** 双机可分别录像、分别回查，结果需人工对照。两台设备也不能保证没有盲区。

## 发现烟头后，回看此前几小时

1. 记录发现烟头的时间与位置；区分“亲眼看到落下”与“后来在地面发现”。如有上次确认地面无烟头的时间，也一并记录。
2. 以发现时间为截止点，先回查此前 3 小时，按需要扩大至上次确认地面干净的时间。不要把发现时间当作掉落时间。
3. 保留原始录像。让当前分段正常结束后再分析已关闭的文件，后续分段可以继续录制；不要用异常终止进程的方式强制封装录像。
4. 系统按时间选择相交录像，分成至多 5 分钟的任务，筛查运动候选。按运动面积分数排序，仅导出配置数量内的候选，**不是对所有烟头事件的完整检出**。
5. 每个候选导出九宫格、6 倍慢放 MP4 和 JSON，人工确认是否为真实下落物体、是否可能是烟头，再回到原始视频核对来源过程。
6. 检查 `report.json` 的缺录/未回查区间、跳过文件及错误；无候选不能当成“无事件”。多机分别跑回查，再根据已测量时钟偏差对照。

### 一条命令回查此前 3 小时

先完成 README 的安装，在项目根目录、已激活虚拟环境的终端运行。以下日期、卷名与输出名是示例，需替换：

```bash
python -m app.review recent \
  '/Volumes/YOUR_DISK/cigarette-butt-monitor-data/recordings/camera01' \
  'outputs/review-20260919-1300-camera01' \
  --discovered-at '2026-09-19T13:00:00' \
  --hours 3 \
  --max-candidates 12
```

**这是人工发现后触发的回查命令**，尚未与实时 AI 候选自动联动。默认仅输出排名靠前的 12 个运动候选，不会自动认定高空抛物。图像帧差不是烟头专用检测模型，鸟、昆虫、树叶、反光、相机抖动等可能排在前面。

要求输入为单台摄像机的录像目录，文件名使用以下任一格式：

- OBS：`2026-09-19 12-00-00.mkv`
- 直连：`camera01_2026-09-19_12-00-00.mkv`

时间由文件名起始时间和媒体时间戳推算，未做帧级绝对授时。`--discovered-at` 使用摄像机电脑文件名采用的当地时间（不带时区后缀）；跨机先换算各自时钟偏差。错误命名不能靠文件修改时间替代。重复启动请指定新的输出目录，程序拒绝覆盖原有回查目录。

输出结构：

```text
report.json                 回查窗口、已处理区间、缺段、错误及候选索引
scans/                      分块运动分析 JSON、候选图片与日志
candidates/001/
  grid_3x3.jpg              九个真实原始帧，按时间从左到右、从上到下
  slow_6x.mp4               1/6 速度播放，约为原片段时长的 6 倍，无音频
  review.json               原片段时间范围、取帧时间、导出文件 SHA-256
```

默认每个候选取约前 1 秒、后 2 秒，裁到回查窗口边界；九宫格在该片段中均匀取 9 帧。6 倍慢放使用原帧重复，不用 AI 插帧补造运动，不能恢复原始录像没有拍到的细节。没有足够可解码帧时报告错误，不用占位画面冒充现场帧。

`status: partial_review` 或退出码 1 表示存在失败或时间缺口；退出码 0 只表示所选时间窗口完成运动筛查，**不表示可靠识别或排除了所有抛物**。坏帧、相机本身丢帧和曝光不足仍需核查。回查消耗 CPU、内存和存储，应优先保证持续录像的资源。

### 人工选定片段后重新导出

如果候选窗口过宽，或需要仔细看下落的某一小段，可直接使用原视频内的秒数：

```bash
python -m app.review export \
  '/path/to/2026-09-19 12-00-00.mkv' \
  'outputs/selected-event' \
  --start 120.2 --end 122.2
```

这段原始 2 秒视频将生成约 12 秒慢放视频及九宫格。导出功能也支持其他文件名；只有按时间查找录像的 `recent` 命令需要规范文件名。裁切与慢放产物属于辅助审阅材料，原始录像应完整保留。

## 人工结论建议

记录“已观察到小物体下落”“疑似烟头，待确认”“来源未拍到”或“片段证据不足”等具体结论；不要用算法候选分数代替确认。分楼层排查的目的在于补足观察范围和寻找连续证据，而不是在未拍到时机械排除某些住户。
